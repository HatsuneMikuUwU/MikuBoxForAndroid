# 冷启动与启动页过渡验证

## 修改

- 删除启动页无条件等待 2 秒的逻辑。保留“显示启动页”设置及首次引导流程。
- 启动图与主页使用同一窗口：主页完成第一次布局后，启动图以 250 ms 淡出，避免等待结束后才创建主页及两个 Activity 之间的淡入淡出。
- Application 不再同步解析全部配置并写入列表镜像；主页先使用已持久化的列表，在 IO 线程同步后刷新。同步入口串行化，避免多个调用同时修改镜像。
- 订阅任务调度移到后台线程；删除主页创建和恢复阶段重复的外观初始化。
- DEX 使用不压缩打包，使 ART 可以直接映射。最终 arm64 Debug APK 的 32 个 DEX 均为 STORED。代价是该 Debug APK 从约 58.1 MiB 增加到 77.56 MiB；本次没有单独证明此项带来的耗时收益。

## 参考与定位

阅读了 MikuRay 的 SplashActivity/MainActivity。上游启动图本身也有 2 秒等待，但默认关闭；本项目此前默认开启，因此不能简单复制其等待逻辑。

Perfetto 捕获显示一次启动的 OpenDexFilesFromOat 约 885 ms，两个 DEX 解压片段约 229/197 ms，主页创建约 688 ms、布局加载约 434 ms。上述片段存在包含关系，不能相加作为总耗时。

## 验证环境和结果

Android 16 arm64 模拟器 `mikubox`，Debug 构建，同一保留数据的模拟器，已有一个 DIRECT-only 配置。每次 force-stop 后从桌面入口启动；这是进程冷启动，不是清空磁盘缓存或重新安装。没有安装 MikuRay 做相同条件的 APK 对比。

| 测量 | 第一次 | 第二次 | 第三次 | 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 修改前，启动入口至主页显示 | 4522 ms | 4193 ms | 4176 ms | 4193 ms |
| 修改后，主页首帧（含启动图） | 2779 ms | 2720 ms | 2619 ms | 2720 ms |

修改前按启动页首帧耗时加上后续主页显示间隔计算；修改后使用 `am start -W` / ActivityTaskManager 的 MainActivity 显示耗时。修改后还会执行名义 250 ms 的启动图淡出，不能把首帧时间直接等同于动画完成时间。不同轮次间重启过模拟器，结果仅作本机方向性证据，不承诺真机提速比例或 60 fps。

重启初期系统后台繁忙时另有 9669/4957/4041 ms，之前系统异常高负载时还有约 17 秒的记录，均保留，不并入稳定后的三次样本。录屏单次首帧为 3042 ms，检查画面确认启动图后直接出现完整主页，过渡中没有第二个空白 Activity 页面。

关闭启动图后的补测最终正常进入主页、配置和选择保持不变，AndroidRuntime 未报告崩溃；但该轮同时出现 Launcher/system_server 超时，`am start -W` 等待 42299 ms 后超时，录屏文件无效，因此未据此报告关闭启动图的耗时或动画结论。

构建验证：Temurin 21 执行 `:app:testDebugUnitTest :app:lintDebug :app:assembleDebug` 成功；27 项测试通过，Lint 0 错误、224 项现存警告。最终 arm64 APK 与模拟器已安装 APK 的 SHA-256 一致：

`52b0c19e367e96dea51682fd17c904917fbe4612898756cde245cf8a4c691d5a`
